# ADR-001: Initial Technology Stack Selection

## Status
Accepted

## Context
Starting the telco-rag-rs project with need to choose initial technology stack for RAG platform. Must balance capabilities, learning goals, and production readiness.

## Decision
Start with PostgreSQL + pgvector + PostgreSQL full-text search for initial vector and lexical search. Use Rust with Tokio + Axum for the backend framework. Provider APIs (embeddings, LLM) abstracted behind traits for future swappability.

## Alternatives Considered
1. **Dedicated vector database (Pinecone/Weaviate/Qdrant) from start**
   - Pros: Scales better, advanced features, separate infrastructure
   - Cons: Additional operational complexity, cost, learning curve, contradicts "architecture-first" approach, premature optimization

2. **Chroma/Milvus locally**
   - Pros: Purpose-built vector search
   - Cons: Extra service to operate, data synchronization, less familiar ecosystem

3. **Pure PostgreSQL from start (no pgvector extension)**
   - Pros: Simplest setup
   - Cons: No vector search capability, would need to add later anyway

## Consequences
- **Positive**: Single database, no extra infrastructure initially, pgvector production-ready, trait-based abstraction for future migration
- **Negative**: Limited scale compared to dedicated systems, may need migration at ~10K+ documents or specific relevance requirements
- **Migration path**: When scale/requirements justify, migrate to dedicated vector database while keeping Rust code identical (trait-based repository abstraction)

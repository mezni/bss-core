# ADR-003: LLM Provider Abstraction Layer

## Status
Accepted

## Context
Need to integrate with LLM providers for the generation stage (Stage 6+) while maintaining ability to switch providers, support fallback/routing, and track costs. LLM calls are the most expensive operation in the RAG pipeline.

## Decision
Abstract LLM provider behind a Rust trait (`LLMProvider`) with the following contract:
- `completion(messages: &[Message], temperature: f32, max_tokens: usize) -> Result<Completion, Error>`: Generate completion
- `model() -> &str`: Current model identifier
- `temperature() -> f32`: Current temperature setting
- `cost_per_token() -> f64`: Current cost per output token
- `supports_function_calling() -> bool`: Whether provider supports function calling

Concrete implementations:
- `OpenAIProvider`: gpt-4o, gpt-4-turbo, gpt-3.5-turbo
- `AnthropicProvider`: claude-3-opus, claude-3-sonnet, claude-3-haiku
- `MockProvider`: For unit testing with deterministic responses

Provider selection via configuration, with automatic fallback on API errors.

## Prompt Construction
- System instruction + retrieved context + user question
- Token budgeting: max tokens limit, truncation strategy for context
- Citation formatting: Inline citations `[1], [2]` mapped to sources list
- Structured output: JSON schema validation for response parsing

## Cost and Usage Tracking
- Tokens per request logged with metric labels (model, provider, stage)
- Cost per query calculated: `input_tokens * cost_per_input + output_tokens * cost_per_output`
- Monthly/per-tenant cost aggregation for billing/allocation
- Budget alerts when projected costs exceed thresholds

## Alternatives Considered
1. **Direct OpenAI calls throughout codebase**
   - Pros: Simplest start
   - Cons: Tight coupling, no fallback, hard to test, no provider switching

2. **Single provider with hard-coded fallback**
   - Pros: Simple logic
   - Cons: Limited flexibility, no A/B testing, poor extensibility

## Consequences
- **Positive**: Testable with mock provider, provider-agnostic, cost tracking, structured outputs, easy A/B testing of models
- **Negative**: More initial implementation, need to implement trait for each provider
- **Stage gate**: Must have abstraction before production consideration (Stage 8)
